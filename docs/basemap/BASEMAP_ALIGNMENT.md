# South-pole imagery basemap — approach, alignment evidence, limits (branch `feature/south-pole-basemap`, NOT merged)

Status: **implemented and verified; awaiting owner review before any merge to main.** Display layer only: no backend, API, engine or science change; no new computed numbers; nothing reads values from the imagery (C4). Started 2026-11-15 09:41 IST; the evidence and the implementation took about 55 of the 90 minutes.

## 1. Approach used: real tile service (approach 1)
**NASA Moon Trek** (`trek.nasa.gov`, JPL/NASA) serves a public WMTS (REST) layer **`LRO_WAC_Mosaic_SPole60_100m_v02`** ("LRO WAC Mosaic, S Pole v2", LROC Wide Angle Camera, 100 m/pixel native, ASU/NASA) in a **south polar stereographic** projection. Found through Trek's own layer catalogue (`IAU2000:30120` layer list); capabilities at `https://trek.nasa.gov/tiles/Moon/SP/LRO_WAC_Mosaic_SPole60_100m_v02/1.0.0/WMTSCapabilities.xml`.
* **CORS** is open (`Access-Control-Allow-Origin: *`); the app draws the tiles as plain SVG images, which needs no CORS anyway. No API key.
* **Projection** (service ImageServer description): `PolarStereographic_Moon`, sphere radius **1 737 400 m**, central meridian 0, standard parallel −90, no false origin, extent ±1 095.7 km, 100 m pixels. This is the same grid as the project's DEM (`IAU:30135`, `dem.py`).
* **Tile grid** (capabilities): `TopLeftCorner (−1 095 930, 1 095 930) m`, 256-px tiles, level 0 = one tile spanning 2 191 860 m, each level halves it; tiles exist for **levels 0–5** (267.6 m/pixel at level 5; native is 100 m, so the service is coarser than the product). The app requests level 2 (2.1 km/pixel): **16 tiles** for the 1000 km disc, far finer than the 340-px map needs.
* **What the app does** (`web/src/components/SiteMap.tsx`, `web/src/polar.ts`): replaces the abstract ring-only background with these tiles under the existing markers; keeps the rings/meridians as an optional overlay (two checkboxes: Lunar imagery, Parallel rings; both on by default); markers and rings are drawn in the **same stereographic grid** as the tiles.
* **Credit shown on screen** (caption, with link): "LRO LROC WAC mosaic, S Pole v2 (NASA/GSFC/Arizona State University), 100 m/pixel native … shown at about 2.1 km/pixel from NASA Moon Trek. It is context only; no calculation uses it."
* **No LOLA dependency:** tiles and markers need only latitude/longitude, so a custom point outside every DEM window still renders (tested with −72°, 200°E). A point north of the 1000 km disc is pinned to the rim and labelled "beyond map edge"; a northern latitude draws nothing.
* **Fallback:** if tiles fail to load (offline, blocked) the map shows the ring schematic, a visible "Imagery unavailable" note, and every marker and ring unchanged.

### Deviation to flag: one formula is repeated in TypeScript
The brief says markers must use the same projection math as `dem.py` and not a second implementation. The browser cannot call Python and no API returns projected coordinates for an arbitrary lat/lon without DEM coverage (`/dem/elevation` needs coverage; adding an endpoint would be a backend change, excluded). `polar.ts` therefore mirrors `lonlat_to_xy` (a three-line formula) and is **pinned to the engine by a generated golden table**: `web/src/polarGolden.json` is produced from the engine; `tests/engine/test_basemap_projection_golden.py` asserts it equals `dem.lonlat_to_xy` (1e-6 m), and `web/src/Basemap.test.tsx` asserts the TypeScript equals the same file. Drift on either side fails a test. Decision S1.
Side effect: the previous schematic used an azimuthal-equidistant layout (colatitude linear), not a true projection; marker positions on the map therefore changed (they now follow the stereographic grid, as the DEM does).

Every measured offset (≤ 0.63 km, most ≤ 0.2 km) is ≤ 0.1 of a screen pixel, and < 0.3 px at the tile's own 2.1 km/pixel. Nothing was nudged: no offsets were applied; the tiles are placed at the service's stated origin.

### What the checks do and do not prove
* They show the tiles are placed correctly in the app's grid to a few hundred metres at worst. They compare two independent datasets (WAC image vs LOLA DEM) that both claim the same frame; a common-mode frame error in both would not show. The only frame-related comfort is that the residual (≈ 0.1–0.2 km) is far below the ~0.9 km a MOON_PA/MOON_ME mix-up would cause.
* The DEM-image correlation depends on an illumination model (azimuth following the polar angle); the shift varies by about ±30 m with it, which is why a range is quoted.
* The Chandrayaan-3 registration uses the 60 m window that is registered but **not owner-validated**; this is supporting evidence, not a validation of that DEM.
* Mosaic seams and uneven lighting are part of the product (e.g. the horizontal seam left of the pole); they are not alignment errors.

## 2b. Click the map to set coordinates (added the same day, same branch)
Clicking the map (not a site marker) converts the click to latitude/longitude with the **inverse of the same projection** (`polarLonLat` in `polar.ts`, a mirror of the engine's `xy_to_lonlat`, pinned by the same golden table: the engine test inverts the golden x/y back to the golden lat/lon, the web test does the same with the TypeScript). The View tab then ticks "Use custom coordinates", fills the latitude/longitude fields, draws the red custom marker and says "Press Compute"; **nothing is requested until Compute** (tested). Clicking a catalogue marker still selects that site instead. Typing in the fields takes over.
* **Resolution is stated on screen:** one screen pixel is 6.3 km, so a pick is good to about ±3.2 km; coordinates are rounded to 0.01° (~0.3 km) to avoid false precision, and the text points to the fields for exact values. The map caption also says terrain data exist only around IM-1, IM-2 and Chandrayaan-3, so most picks will return "terrain data insufficient" (correct behaviour).
* Clicks outside the disc (north of about 58°S) are ignored with a visible note. A pointer readout shows the coordinates under the cursor. Keyboard users use the latitude/longitude fields (the map's keyboard behaviour for catalogue sites is unchanged).
* **Real-browser check** (Chrome, DevTools-driven clicks on the live app): the custom marker is drawn within 0.01 px of the (integer) click position Chrome delivered; four clicks at different latitudes/longitudes filled the fields (e.g. aim −66°, 250°E → form −66.01°, −109.82°E, 2.3 km from the aimed point, the difference being Chrome truncating fractional test coordinates to whole pixels); clicks that landed on the Chandrayaan-3 and IM-2 markers selected those sites instead. Screenshot: `pick_demo.png`.
* No new API call, no backend change; `SiteMap.tsx` still contains no `fetch` and no trigonometry.

## 4. Limitations and things to decide (also `stage9/KNOWN_LIMITATIONS.md` L-P9)
1. **Live external dependency.** Tiles load from NASA's server on every page view. If it is down, slow (observed 2 s typical, one 34 s response) or blocked, the fallback shows the ring schematic; a demo on poor wifi will see it. They are not cached by the app; browsers cache them normally.
2. **Privacy.** The browser requests tiles from `trek.nasa.gov`, so NASA's server sees the visitor's IP and referrer. Nothing from the app's users or data is sent.
3. **Terms.** No Moon Trek-specific licence text was found. NASA's general media guidance applies (credit the source; no implied endorsement) and the credit line is shown; the sources conflict about copyright status of NASA imagery generally and ASU is the LROC credit holder. This is **not a legal review**; confirm Trek/LROC terms before wider public use.
4. **Resolution.** The service stops at 267 m/pixel (native 100 m); the app uses 2.1 km/pixel, enough for orientation only. The imagery is greyscale, lit at low sun with seams, and is not a map of anything the engine computed.
5. Imagery is context. It is not evidence for terrain, illumination or visibility results and is labelled so.
