## Fresh-checkout test (`docker compose up`, empty volume), 15 Nov 2026: FAIL, so documented as a two-step process
1. Plain `docker compose up -d --build`: the container exits with `Data not ready` (missing `naif0012.tls`) and restarts in a loop. Nothing is downloaded automatically.
2. Auto-provisioning was tried (entrypoint runs `provision_data.py --skip-large` when `/data` is not ready): the first attempt failed with repeated `RasterioIOError` reads from NASA PGDA (transient and not reproducible: the same script succeeded minutes later, 40-70 s per window), and the container then restarted and started without terrain. After making the entrypoint retry, the second attempt reached `healthy` on its own in about 3 minutes (kernels plus three small windows).
3. **But** `POST /api/scenarios/evaluate` for IM-2 then returned HTTP 200 with `status: terrain_data_insufficient`, `reason_code: DATA_MISSING` ("dem_cache/im2_20m_r80km.tif" missing): IM-2 needs the 141 MB 80 km window, which the light set excludes (the earlier documentation that IM-2 works from the small windows was wrong). A full automatic download would take 30-60 minutes on first start, so the auto-provisioning was **removed** and the two-step process is documented in the README Quick Start. The full path (`provision_data.py --warm` inside the container, then restart, then evaluate) has not been run end to end.

**Not done:** (1) a vulnerability scan of the image; it needs a scanner (`docker scout`, which sends image metadata to Docker's service, or a scanner image pulled from a registry) and was left for the owner to approve. Run `docker scout cves lunarnav:latest` or `trivy image lunarnav:latest`. (2) `docker compose up` was not run; plain `docker run` was. (3) The data was provided from this machine's already-downloaded `data/` folders, so the download path `provision_data.py` inside the container was not exercised (it was verified separately in the clean virtualenv). (4) Linux/amd64 only; no ARM test.

## Vulnerability scan (docker scout, 15 Nov 2026)
First scan: 0 critical, 4 high (expat x2, zlib x2). The Dockerfile now upgrades `zlib1g` to Debian's fixed build (`1.3.1-1+deb13u1`); rescan: **0 critical, 2 high remain: `expat` 2.9.0-1~deb13u1, CVE-2026-118370 and CVE-2026-117610, marked "not fixed" upstream** (no patched Debian package exists yet). `libexpat1` is needed by rasterio. Re-scan before public launch and rebuild when Debian ships a fix.

## Full NASA download inside the container, and the bundle path (15 Nov 2026, evening)
1. **Bug found and fixed (Dockerfile):** the documented step `docker compose run --entrypoint python lunarnav scripts/provision_data.py --warm` skipped the entrypoint, so the data landed in the container's throwaway layer, not the `/data` volume (a 42-minute download was lost). The data folders are now linked into `/data` at image build time; a probe file written by a plain `--entrypoint python` command now lands in the volume.
2. **Full download (second run, fixed image):** exit 0 in about 40 minutes (kernels, five DEM windows: 51 s, 22 s, 3 s, ~21 min for the 80 km window, ~17 min for Chandrayaan-3; then cache warm-up). The script's own check passed.
3. **But the app refused the result:** `DEM window checksum does not match the recorded manifest` for all five windows. Cause: the files are not byte-identical to the reference extracts (compression output differs between the Linux and Windows builds); the **pixels, georeferencing, CRS and tags are identical** (checked with rasterio for all five windows). The manifest records a hash of the file bytes, which is platform-dependent. (The provisioning container's own check passed only because the extraction script rewrote the manifest inside the discarded container.) **Open fix, needs the owner's decision:** verify a hash of the decoded elevation values and georeferencing instead of the file bytes. Until then the from-NASA download is not a working path inside Docker.
4. **Bundle path: PASS.** `lunarnav-data.tar.gz` (301 MB, 329 files, made by `pack_data.py --with-cache` from the verified local data; SHA-256 `3be42fa54d9090d87dfeb8e8938c56a4dd7e8e4378dde17c4d4edb04cbc259f3`) mounted into a fresh container and volume with `LUNARNAV_DATA_BUNDLE_URL=file:///in/lunarnav-data.tar.gz`: archive digest matched, 324 files verified against `SHA256SUMS`, all five windows checksum-verified, container healthy with no restarts and no manual step. `POST /api/scenarios/evaluate` for IM-2 (15 Jan 2027, 30 days) returned HTTP 200, `supported`: Sun 48.6 % [45.4, 48.9] (geometric 53.3 %), Earth 80.8 % [80.0, 80.9] (geometric 73.5 %), matching the validated figures (served from the bundled cache). An uncached case (IM-2, 11 Mar 2027, 14 days) was computed in 4.4 s: Sun 73.96 % [73.89, 74.07] (geometric 82.2 %), Earth 89.1 % [88.7, 89.3] (geometric 81.5 %).
5. **Not tested:** the bundle over https from a real host (a local `file:` path was used); the bundle on a machine other than this one.

## Fix: platform-independent integrity check (15 Nov 2026, late)
Owner-approved change. `data/manifests/dem_windows.json` now carries `content_sha256` for every window: a SHA-256 over the decoded float32 elevations (NaN canonicalised), the array shape and the six affine terms (`lunarnav.dem.content_sha256`). `DemWindow.load` verifies that when present (the byte-level `sha256` stays as provenance and as the fallback for entries without a content hash). Elevation or georeferencing changes are refused (tests: one changed pixel, a one-pixel shift, an unreadable file; a re-encoded copy with different bytes is accepted). `extract_dem_window.py` records the hash for new extracts.
Evidence: for all five windows the content hash of the Windows reference file equals that of the Linux-extracted copy (the pixels, transform and tags had been compared directly); backend suite 403 passed (was 388; +10 bundle, +5 content-hash tests; one old test that appended a stray byte now changes an elevation instead); the rebuilt image started healthy with no restarts on the volume holding the Linux-downloaded NASA data that the app had refused before, all five windows "checksum verified", and IM-2 evaluate calls returned HTTP 200. **Not captured:** a side-by-side comparison of IM-2 figures from the Linux-downloaded data against the reference figures (the check was interrupted); the identical pixels make a difference unlikely, but it was not measured.
