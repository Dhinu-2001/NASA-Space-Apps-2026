# API Contract

Status: **Stage 2.** Only the endpoints marked IMPLEMENTED exist. Everything else is the planned contract; calling an unbuilt endpoint returns `501 NOT_IMPLEMENTED`.

Machine-readable source of truth: the OpenAPI document generated from the Pydantic models (`docs/openapi.json`, regenerated by `python scripts/export_openapi.py`). The frontend's TypeScript types are generated from it (`npm run gen:api`), so the two sides cannot drift.

## Conventions (all endpoints)

| Topic | Rule |
|---|---|
| Base URL | Backend `http://127.0.0.1:8000`; frontend dev server proxies `/api/*` → backend (prefix stripped) |
| Format | JSON, UTF-8 |
| Time | ISO-8601 UTC with trailing `Z` (e.g. `2027-01-15T00:00:00Z`). Local time is never accepted |
| Angles | Degrees. Longitude **east-positive**, latitude planetocentric (south negative). Azimuth clockwise from local north, 0–360 |
| Lengths | Metres (heights), kilometres only where field name ends `_km` |
| Value labels | Scientific payloads (from Stage 3) carry `data_class`: `measured` \| `calculated` \| `assumed` \| `illustrative` |
| Provenance | Every scientific response carries a `provenance` object: model version, kernel names + SHA-256, DEM product/checksum/resolution/CRS, time step, parameters, assumptions (defined per stage) |
| Request id | Optional request header `x-request-id`; always echoed in the response header and error body |
| Errors | Any non-2xx returns the error body below; no HTML error pages |
| Missing data | Never silently degraded: missing terrain => `DATA_MISSING` / `OUT_OF_DEM_COVERAGE` or an explicit `incomplete` status in the payload |

### Error body

```json
{ "code": "INVALID_INPUT", "message": "…", "field": "lat", "details": {}, "request_id": "ab12cd34ef56" }
```

| code | HTTP | Meaning |
|---|---|---|
| `INVALID_INPUT` | 422 | Malformed/out-of-range input (also request-schema validation) |
| `OUT_OF_DEM_COVERAGE` | 422 | Site/window not covered by available DEM |
| `DATA_MISSING` | 503 | Required kernel/DEM not available locally |
| `EPHEMERIS_OUT_OF_RANGE` | 422 | Time outside supported/validated range (2025-01-01…2035-12-31 validated) |
| `NOT_IMPLEMENTED` | 501 | Endpoint planned but not built in the current stage |
| `INTERNAL` | 500 | Unexpected error (details in server log, correlated by `request_id`) |

## Endpoints

| Method & path | Stage | Status | Purpose |
|---|---|---|---|
| `GET /health` | 1 | IMPLEMENTED | Liveness; model version, env, server UTC time |
| `GET /version` | 1 | IMPLEMENTED | Model/API version, current stage, capability table with honest status |
| `GET /sites` | 2 | IMPLEMENTED | Cited site catalogue (kind: confirmed / intended / candidate), conventions, pending regions |
| `POST /sites/validate` | 2 | IMPLEMENTED | Validate/normalise custom lat/lon; reports DEM coverage (`covered`/`not_covered`) |
| `GET /dem/windows` | 2 | IMPLEMENTED | Extracted DEM windows: extent, pixel size, checksum, validity |
| `GET /dem/elevation?lat&lon[&window_id]` | 2 | IMPLEMENTED | Bilinear LOLA height with provenance; explicit errors, no fallback |
| `POST /ephemeris/series` | 3 | planned | Sun/Earth az/el/range/angular diameter time series |
| `GET /horizon` | 4 | planned | Terrain horizon profile `h(az)` with per-azimuth quality flag |
| `POST /scenarios/evaluate` | 5–6 | planned (returns 501) | Terrain-corrected visibility, intervals, metrics for one scenario |
| `POST /scenarios/compare` | 6 | planned | N scenarios → aligned metrics and deltas |
| `POST /scenarios/delay` | 6 | planned | Baseline + day offsets → comparison |
| `GET /metrics/registry` | 5 | planned | Definition, method, unit, source, assumption, limitation per metric |

### `GET /health` → 200

```json
{ "status": "ok", "service": "lunarnav-api", "model_version": "0.2.0-stage2", "env": "development", "time_utc": "2026-11-14T09:00:00Z" }
```

### `GET /version` → 200

```json
{ "model_version": "0.2.0-stage2", "api_version": "0.1.0", "stage": 2,
  "notice": "Stage 2: site catalogue and DEM elevation lookup only. No ephemeris, horizon or visibility results are produced yet.",
  "capabilities": [ { "key": "dem", "title": "…", "stage": 2, "status": "implemented_unvalidated" } ] }
```
Capability `status` ∈ `not_implemented` | `implemented_unvalidated` | `validated`. The UI must display this status; it may not present a capability as available unless `validated`.

### Planned scenario request (draft, finalised in Stages 5–6)

```json
{ "site": { "lat": -89.5, "lon": 0.0 }, "start_utc": "2027-01-15T00:00:00Z", "duration_days": 30,
  "step_minutes": 15, "observer_height_m": 2.0, "earth_elevation_mask_deg": 0.0 }
```
`observer_height_m` default 2.0 is an **assumption** (decision C9). Scenario identity = SHA-256 of the canonical JSON of the request plus `model_version` (decision C5).

## Versioning
`api_version` follows semver; contract-breaking changes bump the minor version while 0.x. `model_version` changes whenever any calculation changes and is stamped into every result.
